# Known limits — 0.3.0

This is a tested development milestone, not a complete production recovery suite.

- Filesystems: FAT32 single-cluster deleted extraction; exFAT root-directory entries only. NTFS continuation/sparse/compressed/EFS/alternate streams, ext4, full deleted directory reconstruction, original timestamps and FAT32 long names are not implemented. TSK optional dependency is declared but no tested TSK adapter is shipped; installing it does not enable unsupported features.
- NTFS: deleted base-record resident/plain nonresident data and fragmented runlists are supported. Original paths are reconstructed only through surviving, sequence-matched parent records (maximum depth 64); stale/missing references yield no path. Recycle Bin naming requires a unique deleted $I/$R pair in the same surviving SID directory and partition, a valid version-1/2 metadata path, and matching file size. Missing metadata, empty $R streams, directory payloads and ambiguous pairs retain their $R names. Pairing is bounded to 20,000 matching records per scan. All-zero nonempty files remain uncertain. See NTFS.md.
- Sources: raw regular images and explicitly selected Windows drive partitions. EWF, VHD/VHDX/QCOW, compressed images and encrypted containers need conversion/unlocking outside RecoverX. GPT backup recovery and extended MBR partitions are not implemented.
- Carving: contiguous only, maximum 32 MiB. TIFF/RAR/MKV/MP3/FLAC matches are discovery-only. PDF uses first EOF. MP4/MOV do not validate sample tables; SQLite does not run integrity_check or merge WAL. GIF previews only the first frame. No arbitrary text carving.
- Imaging: Windows read-only code is implemented, but hardware qualification is outstanding. The first I/O error aborts imaging; partial temporary images are deleted. No fault-tolerant imaging map or persisted imaging resume. Live drive scans do not support persisted resume. Mounted volumes can change concurrently, so use a write blocker/offline source for consistency.
- Extraction: complete candidates only. No directory-tree export, automatic overwrite, partial-file recovery or interrupted-export resume. Windows uses no-replace rename on the destination volume. POSIX output requires hard-link support.
- Metadata recovery checks present allocation, not historical authenticity. Previously overwritten bytes may look valid. A scan hash is not an original reference hash.
- Reports: at most 10,000 candidates per exported JSON and 10 MiB per browser import; browser holds at most ten reports in memory. Native detailed results remain in SQLite with 200-row pages. Native filename/status/extractability filtering and deterministic sorting operate across all pages; selection applies to the visible page. Saved-report destination checks use the scan's stored source disk, including after selecting a different source.
- Preview: metadata, bounded images and ZIP/Office member listings. Preview reads run in a worker and must match the scan hash. Content previews are capped at 4 MiB, images at 16 million pixels, archive listings at 1,000 members/512 KiB directory; ZIP64 and multi-disk archives are rejected. No archive member is extracted for preview. PDF/video/audio playback and waveforms are not implemented.
- Bridge: optional read-only report API, no browser-controlled scanning or recovery. Default workflow imports reports. HTTP-loopback browser compatibility is unverified.
- Cloud: auth and metadata endpoints require real credentials/migrations. Not an image-processing service. Database integration, quotas and abuse controls need production testing.
- History: the desktop starts with memory-only history. Choosing a persistent folder transactionally merges session scans, candidates, checkpoints and recovery records, preserving existing scans; conflicting IDs abort without replacing either history. Saving is rejected on any physical source disk recorded in the session. Old AppData history is not automatically loaded.
- Distribution: build scripts do not imply a signed installer or public native release. The web workspace is deployed at https://recoverx-flax.vercel.app; authenticated database integration and signed native distribution remain unqualified.

No software recovery of overwritten bytes, TRIM-discarded blocks, inaccessible encryption or unreadable hardware is promised.
